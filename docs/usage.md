# Usage

See [Installation](installation.md) for Python, sandbox and inference setup. First create `nudi.toml` with your provider's settings as described under [Models](#models).

## Run an analysis

Pass a local Harbor task directory containing its task configuration, instructions, environment and grader:

```sh
nudi send-nudis /path/to/task --config nudi.toml --output runs/first
```

The output directory must be new or empty. nudi copies the task for its work and preserves the original task directory.

The default `full` analysis starts the Simulator, the hack inspector and the attack together. The no-hint Attacker attempts start at once; the grader inspector starts when the simulation ends. Problems form only after evidence. Each hack inspector reading that evidences an issue is a new problem as it is recorded, `P1`, `P2` and so on; another reading of a check a problem holds joins that problem. Each finding states its cause, `cause`: one sentence on what the grader trusts that it uses, never how to cheat it. A problem's `cause` is that sentence, or its finding's mechanism in a claim without one. When a finding of invalid work accepted makes a new problem, the judge, one call of the run's inspector model, decides before any Attacker starts for it whether its cause is new or the same as a known cause: it reads the task's instruction, the id and sentence of each cause known then, and the new cause sentence. Two causes are the same only when both name the same trusted thing; that the grader checks too little, or a shared kind of cheat, is no match. A finding of a known cause is a problem of its own under that cause at level 2, and no Attacker attacks it. With no known cause, or for a finding without a cause sentence, no call is made and the cause is new; a cause opened without a sentence, or by a finding of correct work the grader fails, is compared with nothing, and such a finding is never compared. When the judge is unsure, names no known cause or its call fails, with one warning, the cause is new. One finding is judged at a time; the call waits for no inspection to end. Each hack inspector request lists the sentences of the causes a finding can be compared with under `known_causes` and asks for a different cause. An inspector's claim whose mechanism is only a category name, such as `package_oracles`, is refused with a reply asking for one sentence naming the flaw, and nothing is assessed from it. A legitimate or unknown reading makes no problem, and neither does a control probe, one with `control` true, which checks the measurement itself. Each check's finding of a new cause with full guidance gets a full-hint Attacker attempt as soon as a slot is free, and the single (minimal) hint when the full hint was exploited. A no-hint attempt's attack inspector is told no target: it gets `known_causes`, the id and cause sentence of each problem known when the attempt starts, and sets its claim's `cause` to the id of the one the exploit used, or to a new sentence when none fits. A known id makes no problem; the report shows the exploit as a reading of that cause. A new sentence makes the Attacker's own problem, `A1` and so on, which opens a cause of its own with no judge call and is not attacked further. The hack inspector never measures an Attacker episode, so those attempts never become its evidence.

An inspector's check program has the bound grading uses for this task, as a setup program has; one that does not finish in it is stopped, measures nothing and reaches the inspector as a tool failure, not a finding. It must exit 0 and print one JSON object with `observations` and `results` objects and a finite `results.deserved`, the score the cited scoring rule gives the submission from what the check measures; a program that is not valid Python is refused with its line number before any sandbox starts. nudi tests this as soon as the check ends: a check that breaks it gets a reply that starts with `contract`, naming what broke and the repair, the same episode checked again without a setup program, which then runs although its case was measured. A reading that stays unknown gets a reply that starts with `repair`: what nudi still needs and the cheapest route, the same check interpreted again when only the claim lacks something, else the same episode checked again. A positive reward equal to the deserved score while a requirement is violated stays unknown as before; its repair names both readings that resolve it, a deserved score that applies the violated requirement or observations showing the requirement is supported, and prefers neither. A probe's reference excerpt matches its source whatever the whitespace between its words, and a refused probe names the requirement or scoring reference that failed; the probe schema marks the fields it requires. An attack inspector probe's category is its attempt's, `accepted_invalid` or, for valid work, `rejected_valid`; nudi sets it, and its probe schema has no category field. run_experiment returns, with the receipt, a draft reading of what nudi knows: the experiment, episode and check, the category, the native reward key and reward, the requirement and scoring references, the location and capture point, the observation keys the check measured, its deserved score, and the fields the inspector supplies. A session has one open draft at a time: a further run_experiment runs nothing and returns that draft. interpret_experiment completes it with a claim whose schema states its required fields. Neither the probe nor the claim schema admits a field it does not declare, at any depth, so a reference in an undeclared place, such as a hack inspector citation or a citation inside a derivation, is refused as an argument error. interpret_experiment takes the open draft when no experiment is named, and an experiment or check id to repair an earlier interpretation. A claim whose derivation, or any further reading in it, names an observation key the check did not measure is refused at once. An experiment's `revisions` records the reasons nudi refused its claims; it does not record failed submissions or claims the schema rejected as argument errors. A probe that answers an earlier experiment's open reading, as that entry's next step asks, names it in `replaces`; once the probe has a reading, the earlier entry leaves `open`. Another reading of the same category does not resolve it. A check that exits 0 on an experiment whose grading wrote no reward did not fail: its reward is unavailable, "its grading wrote no reward" is that experiment's limit and keeps it in `open`, and the same case is not run again; its session's other measurements and findings stand, and only a repeat of that case makes the session `unobservable`. A session that ends with its draft open leaves that experiment `unfinished`: its reading is unknown with that reason, and an inspector can still complete it by its experiment id.

The grader inspector reads the hack inspector's findings so far as places to look; it does not wait for the hack inspection to end, so a later hack finding is not among them. Each evidenced grader inspector finding is a new problem as it is recorded, `G1`, `G2` and so on, unless another reading of its check made one, and gets the full hint as soon as a slot is free, then the single hint when the full hint was exploited. The run has one attack: it takes no new problem once the hack and grader inspections have ended, and ends when its attempts have. Select a subset with `--analysis`: `hacking` runs the hack inspector and the attack, `simulation` the Simulator and the grader inspector.

```sh
nudi send-nudis /path/to/task --config nudi.toml --analysis hacking --output runs/hacking
nudi send-nudis /path/to/task --config nudi.toml --analysis simulation --episodes 20 --output runs/simulation
```

To try the attack again without inspecting again, see [Rerun the attack](#rerun-the-attack). To analyze several tasks in one command, see [Several environments](#several-environments).

Progress goes to stderr, one line for most events of `RUN/events.jsonl`. After 15 minutes without a line, nudi prints one that gives the time since the analyses began and the inspector sessions and Attacker episodes still open, with the problems they work on, and again after each further 15 quiet minutes. Simulator episodes and judge calls are not counted, so during the simulation it says that no inspector session or Attacker is open.

## Options

| Option | Default | Meaning |
| --- | --- | --- |
| `--analysis` | `full` | `full`, `hacking` or `simulation` |
| `--episodes` | `12` | Ordinary Simulator episodes |
| `--focused-attempts` | `2` | Focused attempts per grader inspector or hack inspection category |
| `--attacker-tries` | `1` | Maximum Attacker attempts per candidate and hint level |
| `--discovery-attempts` | `1` | Attacker attempts without hints, which start with the hack inspector |
| `--minimal-hints`, `--no-minimal-hints` | On | Attempt each candidate the full hint exploited with the single (minimal) hint too |
| `--attack-from` | Unset | Earlier run directory of the same task; copy its inspections and approved requirement list and run only the attack |
| `--requirements` | Unset | TOML file of the task's approved requirements, each with the check observation that measures it; see [Reports](#reports) |
| `--isolated-inspections` | Off | Inspect each ordinary episode in a separate grader investigation |
| `--backend` | `docker` | `docker` or `modal` |
| `--concurrency` | `16` | Sandbox limit, also constrained by local Docker capacity |
| `--spending-cap` | Unset | Stop admitting model calls when known inference cost reaches this USD amount |
| `--time-limit` | Unset | Whole-run limit in minutes. At the limit the run stops, cleans up and reports, as Ctrl-C does |
| `--credentials-file` | Unset | Dotenv file of inference credentials |
| `--workspace-memory-mb` | On Docker the smaller of 512 and the task's memory, on Modal the task's | Memory limit in MiB of an Inspector workspace; experiments and native episodes keep the task's limits |
| `--config` | Unset | TOML configuration file |
| `--output` | Required, here or in TOML | New or empty run directory |

[Parallelization](parallelization.md) says what starts when, how the run's slots are shared and when a container waits or is refused. The `hack` `phase_start` event gives the number of slots as `slots`, and `run_start` lists the phases that will run as `analyses`, only `attack` in a rerun with `--attack-from`. One workspace may still admit one experiment even at `--concurrency 1`, and Attacker retries of the same candidate at the same hint level wait for each other. With focused attempts, the hack inspector starts one focused session per category, each from a fresh conversation with the task and the checklist, and one `other` session, which maps what the grader trusts, measures each trust the learner can break and starts with trusts no listed category covers. Its findings take their family as `category` when one fits, else `other`; the `other` session settles no category of its own, but a failed attempt of it stays in `open` until a later attempt recovers it. A reading of an `other` experiment must give `family`, a short name for the hack family it shows, and the problem whose findings all do carries it as `family`; `report.md` lists these novel families on one line after the problems, only when there is one. A persistence probe goes to the native persistence readback, which runs once per location after the session that named it released its workspace. With `--focused-attempts 0` one broad session measures, as the only session of each category. A hack inspection category stays open after a finding, and its focused session is asked again, up to its attempts, while `open` names a failed attempt of its category that no later attempt recovered, unless the measurement was unavailable; a grader inspector category stops at its first evidenced issue.

Calls already admitted can exceed the spending cap. Unknown inference costs remain unknown; the cap is not a strict billing limit. A call cancelled in flight has no usage, so the report counts it apart from calls with unknown prices. A call that has no response when its episode or session ends without an error, as after an agent timeout, counts among the calls with unknown prices. The report gives each reason a call has no price with its count, also under `configuration.unknown_reasons` in `report.json`: no response before its calls ended, a failed request, or LiteLLM's own pricing error. nudi never guesses a price. Each call in `run.json` has `started`, when nudi admitted it, and `ended`, when its response, failure or the end of its calls was recorded; older records have neither. The report also gives the known cost of each job: Simulator, grader inspector, hack inspector, judge, Attacker, attack inspector and persistence probe; a run from before the judge has a grouping job instead. Modal sandbox costs are separate from the inference cap.

Some tasks take hours, so the time limit has no default. A stop (Ctrl-C or the time limit) keeps what ended before it: the hack inspector's records, every finished Attacker attempt and every problem so far, with the conditions an Attacker tried it under. The grader inspector starts only after the simulation, so a stop can leave its problems untested. A stopped run reports its attack as `cancelled` and unfinished. So that a time limit leaves as few problems untested as it can, every problem's first full-hint attempt runs before discovery, valid work, any retry, the minimal hint and the no-hint attempt that follows it. A valid-work attempt starts only when the task's agent timeout fits in the time left; otherwise its status is `insufficient_time` and the report says it did not start. On Modal, each sandbox of a time-limited run also gets a lifetime of the limit plus 15 minutes, at most 24 hours.

Once 20% or less of a bound is left, nudi tells the agent that works under it in one line, so it can finish first: at the end of each inspector tool reply, error replies included, for the session's model turns (the Deep Agents step limit of 9,999 graph steps, about 4,999 turns per request), the time limit and the spending cap; and at the end of the Attacker's terminal output, for the task's agent timeout, the time limit and the spending cap. run_experiment's description states the task's grading bound, which stops an experiment's setup and its check. Simulator episodes get no such line, so they run as in training. A Simulator episode that the spending cap ends early is graded as Harbor leaves it, and is not representative.

By default each problem gets one full-hint attempt, valid work included; when the full hint was exploited, one single-hint attempt; and when the single hint was exploited, one no-hint attempt. The run also makes one independent no-hint attempt, which starts at once. The single hint says that it marks where one specific flaw is and that only an exploit of that flaw counts. The no-hint attempt that follows a hint gets exactly the independent attempt's instruction, and its attack inspector is told no target either, so it is listed with the no-hint attempts, not under the problem. A step counts as exploited when the attack inspector evidenced an exploit on the Attacker's episode, by any route; an unclear result stops the cascade. A step after one that was not exploited is not run: its condition is `not_needed`. A valid-work candidate gets neither a single-hint nor a following no-hint attempt: both conditions are `not_applicable`. No attempt is retried beyond `--attacker-tries`. Just before an Attacker starts, nudi checks that its finding still stands: when a later reading of its check withdrew it, no Attacker starts, its steps are `withdrawn` and a `withdrawn` event names it. When a later evidenced reading replaced it, the Attacker gets that reading's guidance; when that reading has none for the step, no Attacker starts and the step is `unavailable`, with the reason. With `--no-minimal-hints`, or `minimal_hints = false` in the configuration file, each candidate's minimal and following no-hint conditions are `not_requested`: they keep the attack neither partial nor unknown, `report.json` has `minimal_hints: false` and the Markdown report says minimal hints were not requested.

Use `nudi send-nudis --help` for the complete CLI options.

## Models

Configure your OpenAI-compatible provider for the `simulator`, `inspector` and `attacker` roles under `[models.<role>]`. Set all three roles so every model call uses your chosen provider. Each configured role replaces that role's default model settings in full.

Replace `your-model` with your provider's model ID and `https://api.your-provider.com/v1` with its OpenAI-compatible base URL. Keep the `openai/` prefix to select the OpenAI-compatible API:

```toml
output_dir = "runs/configured"
analysis = "full"

[models.simulator]
model = "openai/your-model"
api_base = "https://api.your-provider.com/v1"
api_key_var = "INFERENCE_API_KEY"

[models.inspector]
model = "openai/your-model"
api_base = "https://api.your-provider.com/v1"
api_key_var = "INFERENCE_API_KEY"

[models.attacker]
model = "openai/your-model"
api_base = "https://api.your-provider.com/v1"
api_key_var = "INFERENCE_API_KEY"
```

Save it as `nudi.toml`, then run:

```sh
nudi send-nudis /path/to/task --config nudi.toml
```

CLI options override TOML values. Relative `output_dir`, `credentials_file` and `attack_from` paths in TOML resolve against the configuration file's directory. `api_key_var` names an environment variable; keep credentials out of the TOML file.

## Reports

Each run writes `report.md` and `report.json` beside its retained records and evidence. The CLI also prints the Markdown report. While the run goes, each confirmation, a finding that makes a problem or an Attacker result that confirms an exploit, and each withdrawal or correction, a later reading of an evidenced finding's check or a finding withdrawn before its Attacker started, rewrites both from the records saved so far, each file replaced whole: this report so far has `status` `running`, its Answer opens "Still running. Results below are what was found so far; the final report replaces this one.", and an analysis still running or without a record yet is no warning. The report at the end replaces it. Completion refers to the selected analyses. An incomplete investigation or missing evidence must not be read as evidence that a task has no flaws.

`--requirements`, or `requirements` in the configuration file (a path relative to that file), names a TOML file of the task's requirements a person approved, one `[[requirement]]` table each with its `text` and the `observation` that measures it; it lists one task's requirements, so a batch refuses it with more than one task. The run records it as `requirements` in `run.json`.

A reading is an exploit or work the grader failed (`accepted_invalid` or `rejected_valid`) only with `marks`: observations of its check, which exited 0, that show it; the reports print the value its check measured for each mark. A reading without marks is no finding yet: the interpretation's reply names the marks to supply (`missing_marks`), the inspection keeps it in `open` with the same words, and the Answer gives its episode and check, its reward, whether that is above or below the score its check measured and what its check observed, with no level. A reading with marks is a problem: it feeds the Attacker and takes its level from the Attacker exploits made with its help, whether or not a list was approved.

The approved list changes only the words. With it, a problem whose reading reads an approved requirement violated names that requirement and has its `type`; a problem of work the grader failed whose reading reads every approved requirement supported is labelled "Correct work failed". A grader inspector reading of a simulation episode is read with that episode's other readings, as the metrics read its completion, so two checks that each read one approved requirement supported together confirm it. One validity read for the observations of several approved requirements at once is read for none of them, since it does not say which it is for. Without that, `type` is null, the line states the measured fact, and work the grader failed is labelled "Work the grader failed" with why completeness is unknown: "completeness is unknown: no approved requirement list was given" or "completeness is unknown: the readings of this episode do not read every approved requirement supported". An empty list is no list: the CLI refuses it. When the Answer lists problems and none has a type, the verdict line counts them, such as "22 problems below gave reward the checks show the work did not earn; 20 were exploited by an Attacker given their help, or found by one. No approved requirement list was given, so nudi does not say which task rule each breaks.", with "withheld reward where the checks measured the marks shown" for work the grader failed, and "The approved requirement list confirms none of them" when a list was given. Without a list confirming it, no line says a grader was cheated or that work was correct. With only readings without marks, it reads "No cheat and no misjudged work was evidenced; the readings below claim one, but none names an observation of its check that shows it." A completion in the metrics, complete or incomplete, counts only when the episode's own readings of the approved requirements agree with it, otherwise it is unknown with that reason or "completeness is unknown: the readings of the approved requirements disagree with it", and the episode is in no cell.

The attack's candidates are the hack inspector's evidenced findings, named `hack-INDEX`, and the grader inspector's, named `grader-INDEX`; `attack.candidates` in `report.json` names each one's `source` inspector and the `location` of the experiment that measured it. Scheduling reads the candidates only, never the problems: the attack tries each check's finding with full guidance.

Each problem keeps its own level and counts, and no agent merges two. `report.json` lists them under `problems`, and `attack.problems` is the same list. An inspector problem is one current evidenced hack or grader inspector reading, the latest of its check. An Attacker attempt is an exploit when the grader rewarded it and its attack inspector's own check measured its work invalid, with marks; nudi reruns no check. An exploit made with a problem's full instructions or only a hint counts for that problem at that help, whatever route it took. An attempt uses the latest reading of its check when it starts, and its `sources` name that reading first, so an exploit made with a reading revised before the Attacker ran counts for that reading's problem. A no-hint exploit is at level 5: read as a known problem's cause it makes no problem, and the report shows it under that cause; otherwise it is a new Attacker problem. An exploit made with help for a finding no current problem holds is a problem of its own, found by the Attacker, at that help's level. Its marks and check are the attack inspector's own first reading; further readings of the same attempt make no further problem. An attempt is `unknown` only when no reading decided whether its work is invalid. A problem's id is `P1`, `G1` or `A1` and so on; otherwise it is its finding's: `hack-INDEX`, `grader-INDEX` or the Attacker's episode.

`report.json` lists under `causes` each cause of two or more shown problems, or with a no-hint exploit read as it, also when none of its problems is shown, with its sentence, its problems, highest level first, `not_attacked`, those after its first that no Attacker attacked, and its level, its problems' best, or 5 when a no-hint exploit was read as its cause. Above the problem lines the Answer then says "Causes, each one thing the grader trusts: a judge compared a finding's cause sentence with the known ones when both existed, and the attack inspector read each no-hint exploit's cause, so both are readings, not measurements. A problem of a known cause is not attacked on its own. Each problem keeps its own level and counts.", then each cause, such as "C1: The grader trusts the answer file; ●●●●● exploit executable by unaided learner; the attack inspector read the no-hint exploit in 0004-attacker as this cause.", with its problems' lines beneath it, each starting "  - ". A problem of a known cause that no Attacker attacked ends its line with "not attacked on its own" instead of a count. Problems no listed cause holds follow. Without such causes, as in older runs, the Answer lists the problems alone.

| `level` | `label` | When |
| --- | --- | --- |
| 2 | ●●○○○ reproduced exploit | an inspector reading evidenced it and no Attacker exploit counted for it |
| 3 | ●●●○○ exploit executable by learner with full information | an Attacker that received full instructions for it made an exploit |
| 4 | ●●●●○ exploit executable by learner with hint | an Attacker that received only a hint for it made an exploit |
| 5 | ●●●●● exploit executable by unaided learner | an Attacker with no extra information made the exploit: an Attacker problem, or a cause such an exploit was read as |

An Attacker problem made with a hint or full instructions written for a finding no current problem holds is at the level of the information given, 4 or 3, and its line says so, such as "with only a hint written for hack-3". Only an exploit by an Attacker that received no hint and no full instructions is at level 5; its line says "with no extra information", as that Attacker got no word of any problem. Historical membership is no evidence: an inspector finding a later reading withdrew, or a problem of an older record or an earlier run that no current reading or exploit of this run holds, is a lead, listed under `attack.leads` with its `id`, `cause` and `origin` and in `report.md` on one line, "Leads, which no evidence confirmed", with no level. An Attacker problem made in this run that no problem shows is no lead. An older attack record still loads, its exploits read again from its attack inspector readings: an exploit made with a problem's help counts for it whatever its rerun measured, and an older no-hint attempt aimed at a finding is a no-hint exploit of its own.

The Answer has one short line per problem, highest level first: its id, the approved requirement it names, its reward, the value its check measured for each mark and that check, the help its Attacker had, its label, at level 2 where it was evidenced, why its work's completeness is unknown, for an inspector problem how many assessed attempts with its help were exploits, such as "P2: reward 1; exists = false measured by check check-0003; ●●●○○ exploit executable by learner with full information; 1 of 1 assessed attempts with its help were exploits.", "no exploit in 2 assessed attempts with its help", "no attempt was assessed" or, for a problem of a known cause, "not attacked on its own". An attempt the grader paid nothing was never inspected, so it is not assessed: the count adds ", and 1 attempt got reward 0". It never says a problem was not exploited. What an agent left unresolved is not in the Answer: `report.md` lists the problems in its Attack section, one line each with its source, label, cause sentence and findings, beneath it what the reading leaves unresolved, which is left out once an Attacker given its help made a native exploit, its cases, and one line per help level its help was given at, such as "With only a hint: 0 of 1 attempts were exploits, MODEL, no_evidenced_issue." or "With only a hint: Not run, no exploit was made with more help." An attempt that did not run or was not judged is not counted: the line adds "Not run or not assessed:" with its episode, reward, status and error, and one the grader paid nothing adds "1 got reward 0, so nudi did not inspect it." Each attempt line in the Attack section names its exploit plainly, such as "an exploit with only a hint written for P3", "an exploit with no extra information" or "an exploit with no extra information, its cause read as P3's"; an unknown attempt's line says what left it undecided, such as "result unclear: no marks: ...". A problem of correct work the grader fails is no exploit: with the approved list confirming the work correct, its `type` is `false_negative` and its label "Correct work failed", the words of `docs/diagrams/simulation.mmd`, otherwise "Work the grader failed", then how an Attacker exploited it. Each attempt in `attack.attempts` has `problem`, the problem its help was written for or, with no hint, whose cause its exploit was read as; [the field reference](report-fields.md) lists the fields.
Readings that evidenced nothing stay among the inspections' `experiments`. The Categories searched section names a category as searched only when a focused attempt, an experiment or a reading names it, not because a broad attempt ran; it lists each inspector's experiments with their category, check and result, the outcome of the check's latest reading or, without one, the experiment's status. It also names each category's `open` entries as its leads and counts each category's latest legitimate readings, a count and no verdict. Beside the leads it lists each "●○○○○ suspected exploit" with its category and check: a hack or grader inspector experiment that was measured but whose reading ended unknown, as when the run ended before the reading was finished, in a category where no evidenced reading has the same case: the same case name, episode or package, location and capture point. A suspected exploit is not a problem: it is not grouped, not attacked and not counted among the problems. A lead with nothing measured gets no such line. When the problems have ids, the line after the problems says where each id's letter comes from: "P: found by the hack inspector's search. G: found by the grader inspector in the simulations. A: found by an Attacker, not among the inspectors' findings." `source` in `report.json` names it too. Each experiment row keeps its probe's `location` and `capture_point`; in older reports a hack inspector experiment whose probe was judged before it ran may have the status `known_problem`. A `judged` event's `finding` is a hack inspector finding (`hack-INDEX`), a grader inspector finding (`grader-INDEX`) or an Attacker episode (`NNNN-attacker`); older runs name a hack inspector experiment (`experiment-NNNN`). The `judged` event records each new problem and each no-hint exploit the attack inspector read as a known cause, with `new` false; a `cause` event records each new problem whose cause the judge read as a known one; `reproduced` records that an inspector finding made a new problem. `attempt_end` comes when an Attacker episode returns, before the attack inspector reads it; each attempt then ends with one `attempt_result` event, with its `episode`, `problem`, `level`, `number` and the `status` saved for it, whatever its outcome; `episode` is null when the attempt stopped before its episode started, as at the spending cap. A run from before problems has none of these fields, and its report still loads. The grader inspection in `report.json` names the hack findings it read under `hack_findings`, and under `hack_inspection` whether that hack inspection was `complete`, `partial`, `failed` or still `running` when the grader inspector started; a hack inspection that failed or still ran gives the findings it had saved.

Each Attacker attempt gets its attack instruction first, then the task's own instruction between `<task>` and `</task>`, then a one-line reminder of its goal. That text is saved as `episodes/<episode>/nudi-evidence/extension.md`.

The report lists the categories searched and the cheats found. Category states stay inside nudi to control the search and remain in `report.json` for compatibility.

Every run_experiment, interpret_experiment and inspection_status reply, also a refusal of the call's arguments, starts with `open`: what keeps the session's categories unsettled, each entry with its `id` (an experiment, episode or category), `category`, `reason` and `next` step. Its sources are an open draft reading; an experiment whose latest reading is unknown, with its reasons and repair, or agrees with the reward but leaves an item unresolved; a failed check or a check that broke the output contract, until a later check of its episode keeps the contract; a case whose measurement was unavailable, as when its grading wrote no reward or its experiment failed, until a different case names it in `replaces`; a failed attempt no later attempt of its category recovered, which a later focused attempt retries; a requested category with no reading that agrees with its reward; and, for the grader inspector, an ordinary episode whose label is unknown. A session sees its own experiments, those it inherited from the grader inspector's broad conversation, and what names its categories or its episode. `replaces` must name an experiment that `open` lists, of the probe's own category and scope: the same episode for a probe of an episode, or a package experiment for a package probe; any other is refused and nothing runs. An experiment a later one of its scope replaced, once that one has a reading, is read through its replacement everywhere, unless its own reading is evidenced, which no replacement withdraws: in `open`, in an attack attempt's result and in the report's findings and suspected exploits. A category settles `no_evidenced_issue` once its sessions ended and no entry names it, and an inspection is `complete` only when `open` is empty. Tool errors, duplicate cases and refused out-of-scope probes are history: they appear in limits and attempts but keep nothing open. A reading of a retained check outside an experiment, such as the attack inspector's reading of a check nudi reran on its episode that made no draft, is in `open` like an experiment's. An ordinary episode without a native reward cannot be labeled: it is listed in limits and keeps nothing open. interpret_experiment accepts only the session's own experiments and checks, a check staying its session's when its measurement failed, and, for a grader inspector session that continues broad's conversation, those of broad; a session that started fresh, as every hack inspector session and a grader inspector session whose broad conversation could not be continued, inherits nothing. Another session's experiment or check is refused, so the session measures its own case. `report.json` keeps what was left open as `inspections.<inspector>.open`, and `report.md` has one line per open category under Categories searched.

When Modal reports that an inspector session's workspace or experiment sandbox ran out of memory, that inspector attempt has the status `out_of_memory`; for an attack inspector session, so does its attack attempt. A Modal sandbox that exited 137, which Harbor reads as out of memory, is named "sandbox killed, out of memory (exit 137)" in every error. A Simulator episode that ended without a reward is named in the Answer's first line with when it ended and its first failure, such as "0000-simulator (during agent work; ModalFailure: Modal exec failed: sandbox killed, out of memory (exit 137))": during grading once nudi had copied its environment for grading, else during agent work. A failed experiment fails only itself: its measurement is unavailable and keeps its category open, not failed. A focused session whose workspace ran out of memory makes no later attempt in it; its category's `open` entry says to run the inspection again. An Attacker episode that runs out of memory, or an attack attempt that fails outside its attack inspector session, keeps its usual failure status, such as `tool_failure`. Docker does not report this to nudi. An Attacker episode that ended with an unclassified error and no reward, such as an agent setup that failed or a grader that wrote no reward, has the status `episode_failure`: it failed to run. An attack attempt's `failed` names the agent whose failure ended it, `Attacker` or `attack inspector`; an attempt whose attack inspector failed keeps the Attacker's reward. nudi's Python 3 probe in an inspector sandbox, its output runner and each check run with `-I -S`, so files in the copied workspace, such as a `sitecustomize`, do not run at interpreter start or change their result. So do the Deep Agents file and search helpers in an inspector's workspace. A check stops after 600 s, as a workspace command does by default; an experiment's setup stops at the task's grading bound. A check therefore imports only the standard library. The interpreter and its standard library are still the copy's own, so a copy that changed them could change a check's output; each assessment from a check keeps this as a limit.

An inspector session that uses all its model turns without returning its summary has the status `step_limit`, with a cause such as "the attack inspector ran out of steps after 4999 turns"; for an attack inspector session, so does its attack attempt.

Grader classification rates require a supported binary reward contract. Unresolved cases are reported separately. `report.md` and the viewer name the counts and rates as `docs/diagrams/simulation.mmd` does: TP (Correct work passed), FP (Incorrect work passed), FN (Correct work failed), TN (Incorrect work failed), FDR (Of accepted work, how much was incorrect?) and FNR (Of correct work, how much was rejected?). Grading analysis for non-binary rubric totals is not supported. When a configuration's native decision rule is grounded in the grader's source, the report also gives its native pass rate over the usable rewards, with a 95% Wilson interval that assumes independent episodes. In `report.json` it is each `pass_rate` under `metrics.confusion`, with the interval as `interval`.

Under Ordinary rewards, each reward of each configuration shows its median, minimum, maximum and skewness beside the mean and SD. When only two values occur, it also shows the share at the higher value with a 95% Wilson interval. From 10 usable rewards, the report can add flags, listed in each reward's `flags` in `report.json` and under Ordinary rewards in `report.md`. `identical_rewards` means every usable reward has the same value. `low_minority` and `high_minority` mean a few rewards lie more than three interquartile ranges below the first quartile or above the third (Tukey's outer fences); the flag names those episodes, their rewards and any timeout, error or refusal they recorded. A flag is a reward pattern that points to episodes worth reading, not a finding. It states no cause and changes no status, exit code, label or rate. With fewer than 10 usable rewards the flags are not evaluated, and the report says so.

`copies` in `run.json` and `report.json` lists nudi's state copies: filesystem copies of the grading environment, taken when grading starts and after the grader returns. `seconds` is the whole copy operation. In `size_bytes` and `pause_seconds`, null means unknown, not zero. On Docker, `size_bytes` is the source container's writable-layer size as `docker inspect --size` reports it, sampled before the commit; it is null when Docker reports no size or cannot compute one. On Modal it is not recorded and stays null, because Modal reports no snapshot size. `pause_seconds` is the elapsed call duration of the `docker commit` or Modal snapshot call, timed by nudi around the call; it is not a measured freeze. Docker pauses the container's processes during the commit, so they were paused for at most that long. Modal does not document whether a snapshot pauses the sandbox's processes. `pause_seconds` is null when the commit or snapshot failed, timed out or was cancelled. A Modal snapshot that fails with `NotFoundError` fails that copy and its experiment; nudi does not retry it.

| Exit code | Meaning |
| --- | --- |
| `0` | Every selected step ran to its end, also when it left evidence unresolved |
| `1` | A step failed or stopped, as at the spending cap or the time limit, or records storage was exhausted |
| `2` | Invalid configuration or startup failure |
| `130` | Interrupted with Ctrl-C; the written report is printed too |
| `143` | Stopped by SIGTERM, as `kill PID` sends; the written report is printed too |

The exit code and `status` in `report.json` say whether the steps ran, not what they found. `status` is `complete` when every selected step ran to its end, `time_limit` when the limit ended the run with no phase failed before it, `partial` when a step failed, stopped, as at the spending cap, or never ran, `stopped` when the model provider refused a call for the account, or in a report that `nudi report` wrote for a run whose process ended without closing it out (see [Report a stopped run](#report-a-stopped-run)), and `running` in the report so far of a run still going. A step that returned `partial` with an attempt that failed to execute, such as an inference or tool failure, an Attacker episode that raised, or a native timeout without a reward or an interpretation, is unfinished unless a later attempt of the same work ended without a failure: the same candidate at the same hint level, or the same inspector category or episode, and every unrestricted category after a failed broad session. The Answer's first line then names the agent that failed and where: "the Attacker failed to run in 0003-attacker", "the attack inspector failed on 0004-attacker, its reward kept", "the hack inspector's focused session of package_oracles failed (out_of_memory)" or "a hack inspector experiment failed: experiment-0002 (out_of_memory)"; an older record that does not say which agent failed reads "an attack attempt failed in ...", and a step without such a record "had an attempt that failed to run". A recovered failure is still lost work: the line reads "Finished, but work was lost: ..." in place of "Every step ran", or adds "work was also lost: ..." after the gaps. It stays in Warnings too, and a step that ends `complete` is never counted failed. `unfinished` names each step that did not run to its end, with its status, and `unresolved` names each step that ran to its end with evidence left unresolved, such as a category or an Attacker attempt the inspectors did not settle; its status in `analyses` is then `partial`, or `not run` for an attack whose findings gave no guidance. The Answer's first line says the same in plain words, also as `outcome` in `report.json`:

- "Finished. Every step ran."
- "Finished with gaps: the hack inspector failed. Results below are what was found." names each step that did not run to its end.
- "Finished, but work was lost: the hack inspector's focused session of package_oracles failed (out_of_memory). Results below are what was found." when every step ran to its end but an attempt or experiment failed on the way.
- "Stopped by you after 0:42. Results below are what was found so far." after Ctrl-C.
- "Stopped by a termination signal after 0:42. Results below are what was found so far." after SIGTERM.
- "Stopped at your time limit after 1:30. Results below are what was found so far."
- "Could not start: ..." with the first reason, when no step ran.
- "Stopped after 0:42: the model provider refused a call of the hack inspector (hack-package_oracles): REASON. Results below are what was found so far." when the provider refused a call for the account, such as at a spend limit, an exhausted quota or an invalid key. nudi then starts no further episode, inspector session or Attacker, ends the running ones, which cannot be warned because a warning needs a model call, names them in Warnings and exits `1`; stderr prints `nudi: stopping the run: ...` and `events.jsonl` has a `provider_refused` event and a `run_end` with `status` `stopped` and the reason as `error`. nudi knows an account refusal by the status 401 or 402, also on a provider error that a rate limit wraps, or by the provider's error code, such as `insufficient_quota` or `invalid_api_key`, never by the message's words: a 403, a content refusal too, or a refusal given only in words fails that call alone. A rate limit, a timeout or a server error is retried as before. A failed call's record keeps the provider's reason with keys and key-like text removed.
- "Stopped: the nudi process ended without closing out the run. Results below are what was found so far." from `nudi report` after the process ended with no chance to save, as after `kill -9`.
- "Still running. Results below are what was found so far; the final report replaces this one." in the report so far.

A finished line adds "Evidence stayed unresolved in ..., so the run may miss more." when a step left evidence unresolved. The time is hours and minutes from the start of the run to its end; a run recorded before nudi kept those times has none. On stderr, each step's last line says what it did, for example `attack done after 0:00:11: 15 attempts, 1 exploit, 2 cases where correct work failed; some results unclear`, where "some results unclear" is a `partial` step and "stopped" a cancelled one. The attack's exploits are confirmed cases where incorrect work passed; a confirmed case where correct work failed is counted apart, and its `phase_end` event gives both as `exploits` and `correct_work_failed`, besides all of its `findings`.

`kill PID` (SIGTERM) stops a run as Ctrl-C does, also a run started in the background, where the shell ignores Ctrl-C; the command then prints `nudi: stopped by a termination signal` and exits `143`. Ctrl-C prints `nudi: stopping: saving what was found` at once, and so does SIGTERM; a repeated Ctrl-C prints it again and changes nothing else. The stop waits at most 30 seconds for the cancelled step, such as a sandbox command that never returns, then saves the records and the report; it waits at most 30 seconds more for the deletion of state copies and 30 more for any other work before it exits, so a stop usually ends within about 2 minutes, except during the final deletion of state copies at the run's own end, which can take several minutes on Modal. Allow at least 3 minutes before a hard kill: a caller that force-kills sooner, as `timeout -k 10s` does, leaves Docker containers running. Work still running then is named in Warnings and left: a Modal sandbox it holds ends at its lifetime, and a Docker container stays until you remove it.

Warnings that libraries nudi uses log through Python logging, such as asyncio's, go to `library.log` in the output folder instead of stderr; with several tasks it is the batch folder's. LiteLLM also prints its own warnings to stderr, through its own handler, and so does a library that writes to stderr itself. Before the command ends, nudi closes LiteLLM's cached connections.

Every field an agent reads in `report.json` and `summary.json` is in the [field reference](report-fields.md).

## Run from an agent or script

A run takes hours, and stdout gets the report only at the end, so start nudi in the background and poll. Send stdout and stderr to files and keep the exit code:

```sh
mkdir -p runs
nohup sh -c 'nudi send-nudis /path/to/task --config nudi.toml --output runs/first > runs/first.md 2> runs/first.err; echo $? > runs/first.exit' > /dev/null 2>&1 &
```

Then check every few minutes:

1. `runs/first.exit` exists: the command ended. Its number is the exit code in the table above. It is the authority on a stop, also after `run_end`: a Ctrl-C or SIGTERM that comes while nudi writes its last report can leave `run_end` and `report.json` saying `complete` while the command exits `130` or `143`.
2. Otherwise `runs/first/events.jsonl` grows, one JSON line per event. The run is over at the line whose `kind` is `run_end`; its `status` says how it ended and its `report` is `report.json`, or null when no report was written. Until then `runs/first/report.json`, once it exists, is the report so far, with `status` `running`. Long silences are normal: a heartbeat line comes after each 15 quiet minutes, and the simulation writes nothing else for about 90 minutes with the default 12 episodes. Silence is not a hang.
3. The command ended with exit code `2` and `events.jsonl` does not exist: nudi refused to start. `runs/first.err` has the one-line reason.

When it is over, read `runs/first/report.json`: `status`, `outcome` and `attack.problems`, as the [field reference](report-fields.md) lists them. The same report is in `runs/first.md`. Exit `0` means every step ran, `1` that a step could not finish or the run stopped, as at the time limit, `2` invalid input or a refused start. These say whether the steps ran, never whether the task can be cheated; that is in `outcome` and `attack.problems`.

To stop the run early, `kill` the `pid` of the first event, `run_start`, not the `sh` around it: nudi saves the records and the report, writes `run_end` and exits `143`. Allow at least 3 minutes before a hard kill, as [Reports](#reports) explains.

If the process ended without a `run_end` line, for example after `kill -9`, run `nudi report runs/first` to write the report from the records.

## Report a stopped run

```sh
nudi report runs/first
```

writes `report.json` and `report.md` again from the run's records, prints the report and exits as the run would have: `0` when every step ran, `1` when a step could not finish or the run stopped, as at the time limit, `2` for a folder without `run.json`. It makes no model call and starts no sandbox. A run whose `events.jsonl` has no `run_end`, such as one whose process was killed, gets `status` `stopped`, also over a report so far that still says `running`: its steps that were still going stay `running` under `unfinished`, and the Answer's first line says the process ended without closing out the run. A run whose `run_end` has `status` `stopped`, such as one whose records host filled at its last write, also gets `status` `stopped`, with that event's `error` in the Answer's first line, even when every step had saved its records. So does a run whose `run_end` has `status` `cancelled`, as after a Ctrl-C or SIGTERM during the final deletion of state copies; its Answer's first line says the run was interrupted. While the run's process still runs on this host, by the `pid` in `run_start`, it refuses with exit code `2`. Pass `--credentials-file` with the run's credentials file so its keys are redacted from the report as in the run's own; keys in the environment are redacted without it.

## Rerun the attack

To try the attack again without inspecting again, name an earlier run of the same task with `--attack-from`:

```sh
nudi send-nudis /path/to/task --config nudi.toml --attack-from runs/first --attacker-tries 3 --output runs/attack-again
```

The new run only reads the earlier run directory. It copies the earlier hack inspection record, the simulation and grader inspection record when that run has them, and every episode and sandbox the earlier run record lists, so the new directory is a whole run that `nudi-view` reads. It does not copy the earlier attack record, but it starts from the problems that record holds, and its event log repeats their `judged` and `reproduced` events, each with `replayed: true` and a text ending "in the earlier run", with no model call. A replayed event is not this run's finding: an Attacker member it names was found in the earlier run. A finding no recorded problem holds, as in a run from before problems, becomes a problem first. The new attack then tries every evidenced problem again from its first full-hint attempt, and makes its no-hint attempts again. It keeps only the earlier problems that were evidenced or that an Attacker found; an earlier problem nothing evidenced is dropped. Each kept problem has `origin`, the earlier run's directory. Its membership there is no evidence here: a kept problem that no current reading or exploit of this run holds is a lead with that `origin` and no level. It reports under the earlier run's approved requirement list, whose words its copied readings were decided with: without `--requirements` it keeps that list, the same list again is accepted, and a different one is refused before anything starts. Each kept problem is a cause of its own, which no new finding is compared with. It runs only the attack and the judge's calls, with this run's models and settings; `--analysis`, `--episodes`, `--focused-attempts` and `--isolated-inspections` do not apply.

A partial or stopped earlier inspection is used as it is. The report keeps its status and names the earlier run in its Answer and in `configuration.attack_from`. An earlier analysis that failed before saving a record, or that stopped, is unfinished: the report is partial, and the Answer names that analysis. Its costs and warnings are this run's; the inspection's cost stays in the earlier run's report. The earlier attack is not copied, but its Attacker episodes are, so they are listed among the other episodes.

nudi refuses before any model call or sandbox when the earlier run has no usable hack inspection record, is a run of another task directory, holds the output directory, lists an episode or sandbox name that is not a single folder name or lists a name twice, or contains a link among the folders and files it would copy. It also refuses a task whose files changed since the earlier run, found by the task digest each earlier sandbox record stores, and an earlier run with no sandbox record to compare, because that run's inspection then may not describe this task; run a new analysis instead.

nudi uses the earlier `run.json` and inspection records as nudi wrote them; episode and sandbox folders hold task output, so their names and links are checked before copying. The earlier run directory may be a link, such as `runs/latest`; nudi then reads the directory it points to, and the report names that directory. The task path check compares the path the earlier run stored, so a relative task path needs the same working directory as the earlier run.

## Several environments

Give several task directories, for example a folder of tasks through a shell glob, to analyze each one in one command:

```sh
nudi send-nudis tasks/*/ --config nudi.toml --output runs/batch-1 --backend modal --spending-cap 10 --concurrency 8
```

With several tasks, `--output` names a new or empty batch folder. It holds one ordinary run folder for each environment, named after its task folder, plus `summary.json` and `summary.md`. Each run folder is what a run of that task alone writes, so `nudi-view`, `nudi cost` and the report read it as usual. With one task the command behaves as before and writes no summary. The CLI prints `summary.md`, not each report, and every progress line on stderr begins with its environment's name. In Python, `send_environments(task_dirs, config, **options)` and `send_environments_async` return the summary and write the batch layout even for one task.

Each summary row gives the environment's task and run folders, its `status`, the `exit_code` it would have alone, its `execution`, the Answer's first line, which says how the run ended, its `answer`, the Answer's verdict line, its `known_cost`, its Modal estimate, its share of the limits and its error, if any. The summary also gives the totals and how they were split. It has no combined verdict, and no finding is grouped across environments.

nudi refuses the whole command with exit code `2` before anything starts when two tasks have the same folder name, the batch folder is not new or empty, the batch folder or the credentials file is inside any task, `--attack-from` is given, or the configuration is invalid. A task that fails the task checks, such as a folder without `task.toml` or a task the backend does not support, is `refused` and the others still run.

The limits are totals for the command, split once at the start over the environments that pass the task checks:

- `--spending-cap`: each environment gets an equal share. An unspent share goes to no other environment.
- `--concurrency`: on Modal at most `concurrency // 2` environments run at once, each with `concurrency` divided by that number and at least 2 containers, so their sandboxes stay within the total; at `--concurrency 1` one environment runs, and its workspace may still admit one experiment, as in a single run. The rest wait in the given order. Each environment starts at least 30 seconds after the one before, also one that takes the place of an environment that ended early, so Modal's App creation rate limit is not met. On Docker environments run one at a time, each with the whole setting.
- `--time-limit`: one deadline for the command, split equally over the rounds in which environments run. An environment that would start after the deadline is `not_started`. Startup and cleanup run outside each share, so the command can end after the deadline.

| Status | Meaning | Exit code alone |
| --- | --- | --- |
| `complete` | Every selected step ran to its end | `0` |
| `time_limit` | Its share of the time ended with no failed phase | `1` |
| `partial` | A step failed or stopped | `1` |
| `stopped` | The model provider refused the account, records storage full or an unexpected error | `1` |
| `refused` | The task checks or the run start refused it, for example for capacity, backend or credentials | `2` |
| `not_started` | The deadline, Ctrl-C or SIGTERM came before its start | None |
| `cancelled` | Running at Ctrl-C; its report is written | `130` |
| `terminated` | Running at SIGTERM; its report is written | `143` |

The command exits `0` when every environment would exit `0` alone, `2` when no environment could start, `130` on Ctrl-C, `143` on SIGTERM and `1` otherwise. When no environment could start, `summary.md` reads "Could not start: no environment started." On Ctrl-C or SIGTERM the running environments write their reports, the waiting ones are `not_started`, and `summary.md` is written and printed.

## Modal cost

On Modal, the report and the viewer show two estimates of the sandbox cost: one at the CPU and memory the sandboxes requested, and one if all used their limits. Neither is a maximum: no recorded bound covers storage or sandboxes still running. Each run's sandboxes go in their own Modal App, `nudi-<run id>`, so the real bill can be read later. At run end nudi stops this App, which ends any sandbox of it still running; a failed stop is a warning with the command to stop it by hand:

```sh
nudi cost runs/first
```

It prints Modal's bill for that run's sandboxes and exits `0`, or prints one line saying why not. Exit `1` means try again later: the line says when, or the billing report failed or has no row for the run yet. Exit `2` means no bill will ever exist: the run used another backend or started no Modal sandbox, or the folder has no readable `run.json`. Modal reports whole hours, about 10 minutes after each hour ends, and only on Team and Enterprise plans. The bill is before credits and covers sandboxes only. nudi monitors this cost and never limits it.

## Viewer

`nudi-view` shows a finished run in the terminal: the result with its problems, each phase with the findings beside it, and the evidence, limitations and references of each finding. It reads only the run's `report.json`, which nudi 0.0.0 or later must have written, and its `events.jsonl` when it follows a run that is still going. Build it from the repository root with Go 1.27.3 or later, as `tui/go.mod` requires:

```sh
(cd tui && go build -o nudi-view .)
```

Then, from the same directory, open a run folder, go straight to the evidence for its problem P2, or to its finding 3:

```sh
tui/nudi-view runs/first
tui/nudi-view runs/first P2
tui/nudi-view runs/first 3
```

A problem id, P, G or A with its number as the report names it, opens the finding that shows the problem: the one the attack tested, else its first finding, else for a problem an Attacker found the attack finding of its episode.

The viewer opens on Results, with the four phase tabs to its left. Use `tab`, `←` and `→`, or `h` and `l`, to move between tabs, `↑` and `↓` to select a row, `enter` to expand it or open its evidence, and the key shown beside a section to expand it. `m` shows the models, `c` the cost and `?` what every symbol means. On a finding, `←` and `→` move between findings, `tab` switches between Evidence, Limitations and References, and `esc` or backspace goes back. `q` or Ctrl-C quits. Pass `--no-intro` to skip the opening animation, which is also skipped when `CI` is set. In a pipe the viewer prints plain text for scripts and agents: the whole report in sections, in the order of the Results tab, or the finding a problem id or N names. `nudi-view --help` lists its options and the related `nudi` commands. It exits `0` for a complete run, whose steps all ran, `1` for any other run, such as one in which a step failed or stopped or one that reached its time limit, and `2` when the folder holds no readable report.

A run with `--backend modal` keeps its folder on the machine that ran nudi. If nudi itself ran on Modal and wrote to a Modal Volume, download the folder first:

```sh
modal volume get VOLUME RUN runs/RUN
tui/nudi-view runs/RUN
```

To watch a run that is still going, follow its folder. The viewer shows the running sessions and Attacker attempts, the attack, the findings so far and whether an Attacker succeeds without any information, from the run's `events.jsonl`, and the finished viewer once nudi writes the report:

```sh
tui/nudi-view --follow runs/first
```

The tabs are the same as for a finished run. The logs say in words what each job worked on and how it ended. `?` explains every column and symbol of the live screen, `l` expands the logs, `o` the related observations and `f` every finding so far; `←` and `→` page the agents in a narrow window. Press `q` to stop following; the viewer then exits `2`, since the run had no report yet. It also exits `2` when nudi's process on this host ended without closing out the run, or when no log began in the folder within 2 minutes. A run on Modal is followed from a copy of its folder downloaded as above, and shows the run as far as that copy goes.

[Viewer contract](viewer.md) lists the fields it reads.

from nudi import send_nudis
