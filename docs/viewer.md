# Viewer contract

`nudi-view` is a terminal viewer for nudi runs, built from [`tui/`](../tui). It reads `RUN/report.json`, and with `--follow` also `RUN/events.jsonl`, and nothing else in the run folder; a file that links outside the folder is refused. nudi decides every word, status and number in those files; the viewer lays them out and never computes a result of its own. [Usage](usage.md#viewer) says how to build and run it.

## Accepted reports

| Report | Viewer |
| --- | --- |
| nudi 0.0.1 and later | Read in full, attack problems included |
| nudi 0.0.0 | Read in full; the attack has no problems, so none are shown |
| Older, without `answer` | Refused: `RUN/report.json comes from a nudi older than 0.0.0, which wrote no answer` |
| Incomplete: an empty `answer`, or a rate with a `value` but no `numerator` or `denominator` | Refused with a message naming the gap |

Fields the viewer does not use are ignored. Python's nulls for statistics it cannot give are shown as unavailable, and so are a missing `known_cost`, a reward statistic that an older report lacks, such as `median`, and a missing `pass_rate`; none is shown as zero. An analysis status or category name the viewer has no words for is shown as written. Category states are not displayed. Control characters and Unicode format characters, such as bidi overrides, are dropped from every string in the report, map keys included, and from the folder name and error messages, before anything is drawn.

## Fields read

| Field | Shown as |
| --- | --- |
| `answer` | The Results tab: the first line as how the run ended, the rest below it |
| `status` | The exit code |
| `analyses` | The phase steps: a phase missing from it was not selected; `not run` and every status are shown as given |
| `warnings` | One Work left row each, naming where, what and why in Python's words. A warning that an attack candidate is unknown or unattempted is left out, since the row of its problem already says it. A coverage warning that a phase ended `partial` is replaced by that phase's open questions, each named with its reference and its reason, or `Reason not recorded`, when the phase has some |
| `configuration` | `task_dir`, `models.ROLE.model` and `reasoning_effort`, `spending_cap`, `known_cost`, `unknown_cost_calls`, `cancelled_calls`, `backend`, `modal_cost.at_requests` and `at_limits` |
| `ordinary` | `requested`, `attempted`, and per group `configuration.model` and `rewards.KEY` with `attempted`, `usable`, `mean`, `median`, `sd`, `skewness` and `distribution`, drawn as the rewards chart, then each of its `flags` as a plain observation, with its `flag` and its `text` as written in the method panel that `?` opens, or `flags_not_evaluated` as written, on the Simulation screen and in the plain report. Absent or null `flags`, a null flag, or a flag without its `flag` or `text` reads flag details unavailable |
| `labels.counts` | The grader inspector's episode labels |
| `metrics.confusion` | Per group: `configuration.model`, `reward`, `status`, `reasons`, `rule`, `tp`, `fp`, `fn`, `tn`, and both rates with `value`, `numerator`, `denominator`, `lower_bound` and `unavailable`; and `pass_rate`, the native pass rate, with the same fields and `interval`, its 95% Wilson interval, worded as in `report.md` on the Grade Simulations screen and in the plain report whatever the group's `status`. An older `pass_rate` without `interval` is shown without one |
| `inspections.grader_inspector`, `inspections.hack_inspector` | `status`, `open`, `categories`, `attempts`, `experiments`, `applicability`, `limits`, and `findings.evidenced`, `inconclusive` and `legitimate` |
| `attack` | `status`, `maximum_attempts`, `candidates` (`id`, `valid_work`, `conditions.LEVEL.status`), `problems` (`cause`, `findings`, `candidate`, `reproduced`, `reproduced_findings`, and for problems formed during the run `id`, `source`, `members`, `exploited_with` (`help_needed` in older reports), `level`, `label`, `exploited_by` and `conditions` (`condition`, `exploited`)), `attempts` (`level`, `candidate`, `sources`, `problem`, `episode`, `status`), `findings`, and `exploits.KIND` (`assessment`, `candidate`, `sources`, and for `other` the `problem` the judge named) |
| `other_episodes.attacker` | Which attempts started |

The viewer also reads facts for screens that tabulate them: `unfinished`, `unresolved`, `elapsed`, `stop`, `phase_errors` and `ungrouped`; `configuration.capacity.concurrency`, `unknown_reasons` and `modal_cost` (`sandboxes`, `without_limits`, `still_running`); per ordinary group `episodes` and `episode_rewards`, and per flag `episodes`, `quartiles`, `fence`, `minimum` and `recorded`; `labels.episodes` and `labels.review`; `metrics.episodes` and `metrics.coverage`; per inspection `open` and each experiment's `id`, `status`, `check` and `episode`; in `attack`, `discovery`, each attempt's `number`, `rewards` and `error`, each exploit's `attempt` and `problem`, each problem's `outcome`, `evidenced_by_inspector` and `exploited_by`, and each condition's `attempts` and `status`. [Report fields](report-fields.md) defines them. A report written before one of them lacks it, and the viewer reads it as not recorded, never as none or zero: a report without `phase_errors` also predates `stop`, so its null `stop` does not say that the run ended on its own.

Each finding is read for `index`, `superseded_by`, `execution_scope`, `category`, `claim` (`mechanism`, `episode`, `unresolved`, `limits`), `captured` (`native_reward`, `copied_grader_reward`, `check.id`, `check.requirement.excerpt` and `path`), `interpretation` (`interpretation`, `citations`) and `assessment` (`outcome`, `reasons`, `limits`).

## Layout rules

These rules arrange the report; none of them changes a result.

- **Findings.** The list holds every evidenced finding whose `superseded_by` is null: the grader inspector's, then the hack inspector's, then the attack's, each in report order, numbered from 1. A hack inspector finding is named `hack-INDEX` and a grader inspector finding `grader-INDEX`, as the attack names its candidates, so a candidate, an attempt or a problem names the number of the finding it came from; an attack finding is named by its check id. An inspector finding without its `index` is named `grader index unavailable` or `hack index unavailable` and links to nothing.
- **Types.** A finding's type comes from who found it and its outcome: `accepted_invalid` is "False positive: incorrect work passed" from the grader inspector and "Hack: the reward was earned without doing the task" from the hack inspector or the attack; `rejected_valid` is "False negative: correct work was rejected" from any of them. A finding's screen is titled by the cause of the problem that holds it, with the finding's own mechanism on a Mechanism line, or by its mechanism when no problem holds it; it names its type in full under its title, then who found it, its problem, where its evidence comes from and the least an Attacker was told when it reproduced the problem. An attack finding adds what its entry in `exploits`, the one whose `assessment` is its `index`, says it confirmed of the findings the attempt tested: reproduced (`reproduction`), another mechanism while testing (`other`), not confirmed as (`unattributed`), or found with no information (`discovery`), each tested finding named by its id and its number, as in `hack-1 (finding 3)`. An attack finding with no entry confirms no tested finding. When the finding lacks its `index`, or any entry is null or lacks its `assessment`, an unmatched finding reads confirmation unavailable instead, so nothing is attributed from missing data. A report without `exploits` shows nothing there. The Limitations tab numbers `claim.unresolved` as open conditions, then the scope limits, each under a short heading; the References tab lists every id the finding names with what it is.
- **Attempts.** An attempt started when its `episode` is listed in `other_episodes.attacker`. An attempt that never started is shown as not tested, whatever its status.
- **Problems.** The attack selects only a problem's `candidate`, so only it is marked selected, then attempted or not tested. The problem's other findings carry no selected, attempted or not tested mark, but they may carry a reproduced mark, since an attempt can test other findings of the problem along with the candidate. Every reproduced mark needs a started attempt that tested that finding: a finding is marked reproduced when `reproduced_findings` names it and a started attempt tested it. A report without `reproduced_findings` marks the candidate reproduced when `reproduced` is true and a started attempt tested the candidate. The hack panel counts the problems.
- **Level.** When the problems carry `exploited_with`, or `help_needed` in older reports, the Results tab, the Attack screen and the plain report list them under PROBLEMS by their `level`, highest first: `id` and `cause`, then the level in the viewer's words, such as ●●●●○ an Attacker given only a hint demonstrated it or ●●○○○ reproduced, no Attacker demonstrated it, else the problem's `label`, with where its findings were evidenced (`scope`) and the reason at level 2, and on the line under it the sources. An `exploited_with` of `elsewhere_minimal` or `elsewhere_full`, an exploit found while the Attacker was aimed at another problem, keeps the level of the help it was given, adds `, while aimed at` and the `target` of its `exploited_by` try at that help (`another problem` without one) in place of the label's own suffix, and is listed after the problems an aimed try demonstrated at that level; a finding's screen gives its Attacker result as `Reproduced with full instructions while aimed at P1`. A report without `label` gets it from `help_needed`, in the same words, and a value without a level there is a reproduced exploit. Leads, the problems no evidence confirmed, get no line each: one dim line counts `attack.leads`, and in older reports the problems at level 1 or not reproduced (`not_reproduced`), "N leads, which no evidence confirmed". The sources are `source` and every other inspector whose finding is among `members`, a hack inspector finding (`hack-INDEX`, or `experiment-NNNN` in older runs) or a grader inspector finding (`grader-INDEX`), as in `from hack inspector + grader inspector`. A problem that a hack or grader inspector found adds `independent attacker` when its `independent` condition exploited it, or in older reports at level 5. To fit the terminal, the cause is shortened first. An attempt with a `problem` is named by it on the Attack screen, and a finding's screen names the problem that holds it by its `id`. Each finding keeps its own screen, `nudi-view RUN P2` for the problem P2 or `nudi-view RUN N`. The plain report's NEXT section, and `enter` on the screens, open the evidence for the highest problem on the list that has an evidenced finding; without one they open finding 1. Reports without `exploited_with` or `help_needed` show the problems as above.
- **Problem columns.** The problems tables on Results and Attack have Hint and Full columns and no No info column: a try given no information is aimed at no problem, and an Attacker problem's level says when an Attacker told nothing made it. Such tries stay listed under a problem's tries and in the block for tries without information. The Results table has a Type column when any problem has a type: the report's `type` in words (Hack, False positive, False negative) when it is set, else from the problem's `outcome`, `accepted_invalid` as Incorrect work passed and `rejected_valid` as Correct work failed, and an Attacker problem without an outcome as Incorrect work passed; incorrect and correct are by the inspector's own check. A problem with neither reads `?`. The plain report gives the same as its Type line. The Inspector column and its legend line appear only when the problems carry `evidenced_by_inspector`. Without `exploits`, an attack finding is held by the first problem whose `members` name its episode and by no other; a finding no problem names reads `Not attributed` under Not counted as problems.
- **Problem rows.** Expanding a problem on Results lists its evidence, then, in reports without the Inspector column, a `Level` row with the problem's level in words, then for an `elsewhere_` exploit a row `Hint ✓` or `Full ✓` that reads `Demonstrated while aimed at` the target, then one row per `-` cell with why that level was not tested: how the try aimed at it ended, else its condition's status, else `Reason not recorded`. The Attack screen groups the problems by that type: Hacks (Hack or False positive), Incorrect Work Passed, Correct Work Rejected (False negative), Correct Work Failed and, for a problem with neither, Type Unknown; when no problem has a type, one group, Problems. Older reports without problems list their tries with `Problem demonstrated?`.
- **Schema 3.** An inspector problem's cells come from its `conditions`: ✓ when an assessed attempt at that help was an exploit, ✗ when attempts at that help were assessed and none was an exploit, `?` when the only attempts got reward 0 (`unrewarded`), which nudi did not inspect, and `-` when none ran. An Attacker problem is ✓ at the help of its own attempt when that is a hint or full instructions. A try's Succeeded is ✓ for `evidenced_issue`, ✗ for an assessed `no_evidenced_issue` and `?` otherwise; under it a try the grader paid nothing reads `The grader paid nothing, so nudi did not inspect it.`, and one with status `unknown` reads `Result unclear:` and the first line of its `error`. The plain report says `not inspected` for such a try. A try given no information counts for no inspector problem, whatever candidate it started for; it is a row of the block for tries without information, whose last column, `Same cause as`, gives the cause of the problem in its `problem`. The viewer does not read `causes`: the Answer's causes paragraph, its `C1: ...` lines and the problem lines under them, which start `  - ` and keep that indent when wrapped, are shown as written: on Results folded under one line, `Causes (N)` with N the `C` lines, that `a` opens, below the ending; in the plain report's Summary under the verdict, unfolded. Schema 2 reports get the same cells, except that a try given no information still counts for its candidate's problem; their rerun, noted and same-as fields are not shown.
- **Not counted as problems.** Evidenced findings that no problem holds read `Standalone evidence`; their rows are selectable, and `enter` opens the finding. A suspected exploit, a measured check whose reading ended unknown, reads `Suspected exploit` with its category as the finding and its check as the reference; it appears only when the report has one. When the same check is also an unresolved finding, that finding's row reads `Suspected exploit` instead, so one reading is one row.
- **Open questions.** Work left and the panels' open questions name each question with its reference and why it is open, or `Reason not recorded`. A phase in `unresolved` adds its unresolved findings, with the reason the finding records. The Results banner of a run with no problem reads `No problems demonstrated in this run.`
- **Help and models.** `?` explains every symbol and defines F1, AUROC and the score ordering AUROC needs. `m` lists each model role with its model, reasoning effort and the jobs it runs. Find Hacks names Attackers beside the Hack Inspector only when the run selected the attack.
- **Search.** The grader and hack panels list the category names searched. Findings appear separately. Search scope comes from retained attempts, experiments and findings. Exclusions, attempt summaries and incomplete-work reasons remain visible. Older reports still load; generated category warnings retain their concrete reasons without verdicts, and the safety disclaimer is omitted.
## Output and exit codes

In a terminal the viewer opens on the Results tab and prints the header and Results tab into the scrollback when it quits. In a pipe it prints the plain report, or finding N with its Evidence, Limitations and References tabs, as plain text 100 columns wide. The plain report has one section per part of the Results tab, in its order: RUN, RESULT, PROBLEMS, EVIDENCE, NOT COUNTED AS PROBLEMS, SIMULATION, GRADER ACCURACY, ATTACK ATTEMPTS, WORK LEFT, COST and NEXT. Each section holds one labelled field per line, with every id in full, no colour and nothing cut; a long value wraps at spaces, and a word too long for its column, such as a path, moves whole to a line of its own.

| Exit code | Meaning |
| --- | --- |
| `0` | The run is complete, as nudi's own exit code |
| `1` | A step failed or stopped, also at the time limit. Evidence left unresolved by a step that ran to its end does not make a run partial |
| `2` | No `report.json`, one linked from outside the folder, a report older than nudi 0.0.0, an incomplete or unreadable report, or wrong arguments; with `--follow`, also the cases that [follow mode](#follow-mode) lists |

## Event log

Every run also writes `RUN/events.jsonl`, so a reader can follow the run while it goes on. `nudi send-nudis`, `send_nudis` and `send_nudis_async` all write it; the viewer reads it in [follow mode](#follow-mode). Each line is one event, a JSON object in UTF-8 that ends with a newline. The log adds a file and changes no other file or report field.

Every event has these fields:

| Field | Meaning |
| --- | --- |
| `v` | The format version, `1` |
| `time` | When nudi wrote the event, in UTC as ISO 8601 with microseconds, such as `2026-11-07T09:15:02.123456+00:00` |
| `kind` | What happened, one of the kinds below |
| `text` | The line `nudi send-nudis` prints on stderr for the event, without its newline: `nudi: `, `time` as `HH:MM:SS` in the host's time zone, and the message |
| `known_cost`, `unknown_cost_calls`, `cancelled_calls` | The run's cost so far, as `run.json` has it when nudi writes the event: the known inference cost in US dollars, the calls of unknown cost other than cancelled ones, and the calls cancelled in flight |

Each kind adds its own fields. Null means the field does not apply to that event.

| Kind | Written when | Fields |
| --- | --- | --- |
| `run_start` | The run's settings, credentials and backend are accepted and its folder exists. It is the first event. | `run_id`; `backend`, `docker` or `modal`; `docker_cpus` and `docker_memory_mb`, null on Modal; `host_cpus` and `host_memory_mb`, the CPUs and memory of the host that runs nudi, on Modal only and null on Docker; `free_bytes`, the free space where records go; `docker_free_bytes`, the free space where Docker stores data, null on Modal and when nudi cannot measure it, as for Docker Desktop, another virtual machine or a remote daemon; `spending_cap`, in US dollars, null without one; `concurrency` and `concurrency_setting`; `reason`, why concurrency is below the setting, or the capacity warning; `pid`, nudi's process id, and `host`, the name of the host it runs on, so a reader on that host can tell whether the run still goes on; `analyses`, the selected analyses in run order, with the names `phase_start` uses |
| `reused` | A rerun of the attack (`attack_from`) starts copying the earlier run, after `run_start` and before any analysis. A copy that fails ends the run, and `run_end` follows. | `earlier`, the earlier run directory as nudi read it; `analyses`, the analyses taken from it in run order, with the names `analyses` uses in `report.json`; `episodes` and `sandboxes`, how many episode and sandbox folders it copies |
| `phase_start` | An analysis starts | `phase`: `simulation`, `grader`, `hack` or `attack`, the names `analyses` uses in `report.json`; `slots`, for `hack` only, how many of its inspector sessions and Attacker episodes run at once |
| `phase_end` | An analysis ends | `phase`; `elapsed`, its duration in whole seconds; `status`, the status the analysis returned, or `stopped` when a task environment cannot start, which stops the other analyses, or `cancelled` for an analysis that such a stop or a full disk ended, or `failed`; `error` with `stopped` and `failed`. A returned analysis adds its counts: `episodes` and `requested` for `simulation`, `experiments` and `assessments` for `grader` and `hack`, `attempts`, `findings`, and of those `exploits`, incorrect work passed, and `correct_work_failed` for `attack` |
| `session_start` | An inspector session starts | `inspector`: `grader`, `hack`, or `attack` for the attack inspector; `session`, the session's name in its inspection record; `category`, the one category a focused session inspects; `episode`, the one episode an episode session judges; `problem`, for an attack inspector session, the problem its attempt targets |
| `session_end` | That session ends, after a failure or a cancellation too | `inspector`, `session`, `elapsed`; `status`, the lifecycle status of the session's last attempt; `result`, what the session's own work came to: `evidenced_issue` when a reading it completed evidenced an issue, `open` when `open` still names its work or its last attempt failed, otherwise `no_evidenced_issue`; `category`, the one category the session inspects, a focused session's or the inspection's only one, null for a session over several; `category_status`, retained for compatibility as internal search state; it and category verdicts do not appear in the terminal line, which names the searched category and retains operational outcomes; the viewer normalizes generated legacy lines the same way for plain follow output and live recent lines |
| `evidenced` | An inspector's assessment is evidenced | `inspector`; `outcome`, `accepted_invalid` or `rejected_valid`; `category`, when it is an approved category; `id`, the reading's check id, or its experiment id when it has no check; `index`, the assessment's position in that inspection's assessments, so a hack inspector finding is `hack-INDEX`; `episode`, the episode or package sandbox the assessment graded, for the attack inspector the Attacker episode of `attempt_start` |
| `attempt_start` | An Attacker episode starts | `episode`; `candidate`, null for discovery; `level`, `full`, `minimal` or `none`; `number`; `problem`, the problem a hinted attempt targets |
| `attempt_end` | That episode returned, before its attack inspector | The same fields, `elapsed`, and `rewards`: the episode's reward values in order, with null for a value that is not a finite number |
| `attempt_result` | An attempt's status is saved, once per attempt: after its attack inspector and the judge, and also after zero reward, which needs no attack inspector, an error, a cancellation or the spending cap, also one that stopped an attempt before its episode started, with no `attempt_start` | `episode`, null when the episode never started; `number`; `problem`, the problem it targeted, or the one the judge named for a zero-info exploit, null without one; `level`; `status`, the attempt's status as `report.json` saves it, such as `evidenced_issue` for an exploit of its problem, `other_exploit` for an exploit of another mechanism, `unattributed_exploit` for an exploit nudi could not attribute, or `no_evidenced_issue`. An attack inspector session's own status is not the attempt's |
| `judged` | A finding makes a new problem, or the attack inspector read a no-hint exploit as a known problem's cause. A rerun of the attack first repeats the earlier run's events | `inspector`, `hack`, `grader` or `attack`; `finding`, a hack inspector finding (`hack-INDEX`; `experiment-NNNN` in older runs), a grader inspector finding (`grader-INDEX`) or an Attacker episode; `problem`, its id, `P`, `G` or `A` and a number, the known problem's when not new; `new`; `cause`, the new problem's cause sentence, or its finding's mechanism without one; `replayed`, true when a rerun repeats the earlier run's event for this log. Older logs also have the judge's `reason`, `same_as` and `request` |
| `cause` | The judge read a new problem's cause as a known cause, so no Attacker attacks it | `finding`; `problem`, the new problem; `cause`, the known cause's id |
| `reproduced` | An inspector finding evidences a problem that was not yet evidenced, or a rerun of the attack starts from the earlier run's evidenced problems | `problem`; `result`, `evidenced` (older logs also have `not_reproduced`); `replayed`, true when a rerun repeats the earlier run's evidence. A later event for the same problem replaces the earlier. This is inspector evidence; `attack.problems[].reproduced` in `report.json` says instead that an Attacker reproduced the problem |
| `provider_refused` | The model provider refused a call for the account, as at a spend limit, and the run stops all its work | `agent`, the agent whose call it was; `reason`, the provider's reason with keys removed; `running`, the inspector sessions and Attacker episodes it stopped |
| `revised` | An inspector reads a check again whose earlier reading was evidenced, withdrawing or correcting that finding | `inspector`; `id`, the check id; `index`, the new reading's assessment index; `before` and `after`, the two outcomes |
| `withdrawn` | A finding a later reading withdrew gets no Attacker, which is checked just before the Attacker would start | `candidate`, the finding; `problem`; `level` |
| `warning` | nudi records a run warning that no other kind reports; `run.json` lists it too | `message` |
| `heartbeat` | 15 minutes passed with no other line on stderr; again after each further 15 quiet minutes | `jobs`, the inspector sessions and Attacker episodes still open, counted by job: `Attacker`, `hack inspector session`, `grader inspector session` or `attack inspector session`. The text gives the time since the analyses began and names the problems the open jobs work on, such as `still running after 3:10:00: 1 hack inspector session; 2 Attackers on P1, P2` |
| `time_limit` | The run reaches its `time_limit` | `phases`, the analyses it stopped, and `minutes` |
| `run_end` | The run ends after attempting cleanup and report writing, also after Ctrl-C, the time limit or an error. It is the last event, when nudi can write it. | `status`: the report's `status`, `complete`, `partial` or `time_limit`, or `cancelled`, or `stopped` with `error`; `report`, `report.json` when it was written, which is the report so far, with `status` `running`, when the final one could not be written |

How to read it:

- Lines are in the order nudi wrote them. A reader orders events by line, since `time` follows the host's clock, which can be set back.
- nudi writes one event at a time and closes the file after each, so a reader sees each event as soon as nudi goes on. Sessions and attempts that run at once add whole lines, never parts of one.
- While the run goes on, the last line can lack its newline because nudi is still writing it. A reader parses a line only once its newline is there.
- If nudi cannot write an event, for lack of space or another storage error, it writes no more events for that run. The log is then a whole prefix of the run's events; the failed write can leave part of its event as a last line without a newline. A log without `run_end` is incomplete.
- `status` in `phase_end`, `session_end` and `attempt_result` is an open set: later versions of nudi add values, and a reader shows a value it does not know as text.
- A reader ignores kinds and fields it does not know: later versions of nudi add them and keep `v` at 1. A change to the meaning of a kind or field raises `v`, and a reader skips events whose `v` it does not know.
- Event strings can hold text that a model or a task wrote, and JSON decoding restores any control character in it. Before terminal or plain-text output, a reader removes control and Unicode format characters, such as bidi overrides, from every decoded string and map key it shows, `text`, `message`, `error` and every id included, as the viewer does for the report.

What the log leaves out:

- The command prints every event's `text` except that of `run_end`, since it then prints the report on stdout. After Ctrl-C or a full disk it prints one more line of its own, which says whether the report was written. When an event cannot be written, the log stops silently after that first failed write. The command prints no line about it and still prints that event's text.
- A program that starts nudi must read or discard its stderr while the run goes on. nudi writes each line there before it continues, so a full pipe pauses the run until it is read.
- Errors before the run starts, such as invalid configuration, an output folder that is not empty or an unavailable backend, are printed only; there is no log yet.
- Phase events, `reused` and `run_end` come from `send_nudis`, `send_nudis_async` and `nudi send-nudis`. A program that calls `start_run` and one analysis itself gets `run_start` and that analysis' own events only. `nudi cost` writes nothing to the log.
- An analysis stopped by Ctrl-C or the time limit has no `phase_end`, and an Attacker episode that ends with an error has no `attempt_end`. `run_end` still follows.
- The log misses every event nudi cannot write, `run_end` included, and those after it. The run goes on and ends as it would have without the log; a full disk still stops it, through its other records.
- Model calls are not events; `run.json` lists them, and every event has the cost so far. Simulator episodes are not events either, so the simulation shows only its `phase_start` and `phase_end`, and an attack finding is in `report.json` only.

## Follow mode

`nudi-view --follow RUN` shows a run that is still going, from its event log, and then the finished viewer once the run is over. The folder must exist; the log need not exist yet, and until it does the screen says that it waits for it. A folder whose log has not begun after 2 minutes stops the follow.

- **Reading.** Once a second the viewer reads what nudi added to `RUN/events.jsonl` since the last read. It parses whole lines only, so a last line that lacks its newline waits for the next read. Every string is cleaned as the report's strings are, before anything is drawn.
- **Refusals.** A line that is not a JSON object, a field of the wrong type, or a `v` other than `1` stops the follow with an error that names the file and line. Unlike the general reader rule above, the viewer does not skip an event of an unknown version, since a screen that skipped it would no longer match the run.
- **The end.** Once `report.json` reads in full with a `status` other than `running`, the viewer shows it as for a finished run. A report with `status` `running` is the report so far, which nudi rewrites after each confirmation; the viewer keeps following. After `run_end` the report is final: a `run_end` without `report`, a `report.json` that does not read, or one still `running`, as when the final report could not be written, stops the follow with that error, naming `nudi report` for the last. A log without `run_end` whose `run_start` names this host and a `pid` that no longer runs stops the follow too, naming `nudi report` to write the report. A run on another host, or a log whose `run_start` has no `pid`, is followed until it ends or the viewer is quit.
- **Modal.** The viewer follows a folder on this machine. A run whose folder is on a Modal Volume is followed from a downloaded copy, which shows the run only as far as the copy goes.

The live screen shares the finished viewer's header and tab strip, and lays out what the events say without a status of its own:

| Part | From the events |
| --- | --- |
| Header | `following live`, `backend`, the time since `run_start` by this machine's clock, the latest event's `known_cost` against `spending_cap`, and `concurrency` of `concurrency_setting` |
| Tabs | One tab per analysis that `run_start` lists in `analyses`, then Results. Only the running phase's tab shows the findings so far, the related observations, the Attacker with no information and the logs; another phase's tab shows its phase line, its error or the time limit, and its own agents: none for Simulation, grader inspector sessions for Grade Simulations, hack inspector sessions for Find Hacks, Attackers and attack inspector sessions for Attack. A tab shows a spinner while its phase runs, the Attack tab also while Attacker or attack inspector sessions run; `waiting` before its `phase_start`; a check, `partly`, `stopped` or `Error` after its `phase_end`; a `partial` phase shows `partly`, since the events do not say whether each of its attempts ran. A phase whose `phase_end` has an `error` shows that error and the time the run ended on its tab |
| Agents | One tile per hack inspector, grader inspector and attack inspector session between its `session_start` and `session_end`, and per Attacker episode between its `attempt_start` and `attempt_end`: its job in title case and the time since it started in the top edge, then what it works on in words. A hack inspector session reads General search or Focused search with its `category`; a grader inspector session General review or Episode review with its episode; an Attacker its `problem`'s cause and how much it was told, or "No information, looking for any hack" for a `none` attempt; an attack inspector the try and level it checks. When the tiles do not fit, the row pages with Left and Right as `Agents 1-3 of 5`. An analysis's `phase_end` takes off its own tiles, so the other analyses' tiles stay; `run_end` takes off the rest |
| Findings so far | One row per problem from `judged` events with `new`, by its `problem`'s cause: P rows, then G rows, then A rows judged new for an Attacker attempt aimed at another problem, in log order. The columns are `New?`, whether `novelty_judge` judged it new; `Inspector?`, the reproduction from `reproduced`, `-` for an A row, ✗ after a `withdrawn` event for the problem; `Full instr.?` and `Hint?`, ✓ when `novelty_judge` put an Attacker attempt at that level in the problem, else the latest Attacker attempt aimed at the problem with full instructions and with only a hint. A cell is ✓ or ✗, `-` for not tested, `?` for unresolved, and a spinner while its attempt runs. Help, behind `?`, explains each column and symbol. A replayed problem from an earlier run is drawn as it was, never as new |
| Related observations | `judged` events without `new`, collapsed under `o`: the finding's reference, who found it, whether it is new and the problem it is the same as |
| Can an Attacker succeed without any information? | Its own block, never a row of the findings: one row per `none` attempt with its try, status, whether it demonstrated a hack (any hack, so `other_exploit` is ✓), whether `novelty_judge` judged that hack new, and the problem it matched: once the attempt is settled, the problem `novelty_judge` put its episode in. A rerun's replayed A problem from a guided try is a row of the findings so far |
| Logs | The latest four events, or all kept with `l`, each labelled with its time and the job that wrote it: `novelty_judge` for `judged`, Attacker for `attempt_*` events, the inspector for inspector events, otherwise nudi. Each event is put in words from its fields when they say more than nudi's text: what the job worked on, the problem's cause rather than its id, how much the Attacker was told and how it ended, such as `New finding: CAUSE`, `Started: check of try 1 with only a hint, for CAUSE` `Demonstrated: try 1 with full instructions, for CAUSE` or, for `withdrawn`, `Not started, a later reading withdrew the finding: with full instructions, for CAUSE`; a `revised` event reads `Read a check again: its earlier finding is withdrawn or corrected`; a `judged` event without `new` from the attack inspector reads `Read as the cause of an earlier finding: CAUSE`; a `cause` event is not shown, nor the same event under its older name; other events keep nudi's text, and `--follow` in a pipe prints nudi's text as written. Help, behind `?`, lists only the keys and symbols of the live screen, says that `partly` can include unresolved results, and lists the references |
| Results | `Run not finished` with the time it has run, then the sections of a finished run until the final report is written: PROBLEMS, the findings so far, with the Attacker with no information under them; Not counted as problems, SIMULATION REWARDS, GRADER ACCURACY and WORK LEFT, each reading `Available when the run ends.`; and COST. The problem count leaves out a withdrawn problem unless an Attacker exploited it |

When the window is short, the agent tiles take one row and the findings keep at least two rows with `+N more ↓`; `f` opens them all. When no row fits, a single line reads `FINDINGS SO FAR (N)   f open`; a table header never stands without rows.

The events do not carry all that the finished screens show, so the live screen leaves out the models, a limit per session or attempt, the Simulator's episodes, a description of each related observation, how the findings are later settled or superseded, and the time limit before it is reached.

| Exit code with `--follow` | Meaning |
| --- | --- |
| As without `--follow` | The report was read in full and shown |
| `2` | The folder does not exist, its log did not begin within 2 minutes, a log line is refused, the run ended without a readable report, nudi's process ended without `run_end`, the viewer was quit before nudi wrote the report, or a finding number was given |

In a pipe, `--follow` prints the `text` of each event as the viewer reads it, then the plain report.
